LTisatisのblog｜下一步美化与性能提升方案
日期：2026-10-18

建议顺序：角色启动 → 持续帧率与媒体调度 → 阅读体验与首页层级。
延续双角色、粉白配色与兴趣拼贴，让打开时更快出现细节动作，阅读时拥有稳定底色。

一、依据与适用范围

本次检查了当前源代码、角色清单与素材、2026-10-17 本地构建、现有浏览器测试和验收记录，并查看了 10 月 17 日保存的桌面、手机页面截图。在线浏览工具返回超时，未获得新的线上加载瀑布、真机帧率或核心网页指标。
以下区分“代码和文件已确认”“历史实测”“实施目标”；目标数值不是本次实测结果。
本文件是实施方案，本次未修改网站功能、提交代码或发布。
承接 docs/下一步美化方案-2026-10-15.txt；角色动画、网页音频和视频封面已经存在，本轮优化现有实现。

二、为什么人物出现后，头发和眨眼仍要等一段时间

当前启动链：
静态人物图显示／整图轻微移动
→ 动态导入角色渲染器
→ WebGL 初始化
→ 下载 rigs.json
→ 安奈的身体、刘海、眉毛依次下载和解码，再按眼睛加载三种状态
→ 索尼娅重复上述步骤
→ 两人全部就绪，统一切换到画布
→ 重新安排首次眨眼时间。

已确认的问题：

1. 资源加载存在串行等待，是首要优化点。
src/scripts/character-renderer.ts:152、207、209：角色外层循环串行，每人 5 个部件逐个 await；每只眼睛的 3 张状态图并行，但两只眼睛之间及两名角色之间仍串行。
合计 22 张活动贴图、14 组串行加载/解码阶段。src/scripts/character-renderer.ts:250 在两人全部完成后才挂载画布。
这会把多次请求往返和图片解码等待串起来。延迟的绝对秒数还需在用户实际网络上测量。

2. 加载完成后，首次眨眼还有额外的 3～7 秒等待。
src/scripts/character-animation.ts:71 的 reschedule() 将 nextBlink 设为当前时间 + 3～7 秒。
src/scripts/character-renderer.ts:583 的 seedTime() 接续整图移动时再次调用 reschedule()。
因此正常自动播放路径下，用户看见第一次眨眼的时间大致为“完整动画就绪时间 + 3～7 秒”；点击招手触发眨眼属于另一条路径。

3. 先动的整张图无法独立眨眼或摆动发梢。
src/scripts/character-motion.ts:58 的过渡方案只改变整张图片的位置、旋转和呼吸位移。
它能避免人物完全静止，但不能证明细节动画已经准备好；现有测试主要检查整图运动与最终就绪，缺少首次发梢变形、首次眨眼的时限。
头发弹簧初值为零，seedTime() 只设置时钟，并未推进弹簧状态，接管后的风动还需要建立连续状态。

4. 背景媒体可能与角色贴图争用带宽及解码资源。
src/scripts/ambient-media.ts:47 等 window.load 后 1.2 秒允许背景播放；之后每隔 0.4 秒启动下一段可见视频。这是依次开始请求，并不等待上一段下载结束。
该延迟仅属于背景视频，并不是角色启动定时器。角色加载较慢时，两条加载链可能重叠。
背景固定铺满视口，处于文字卡片后面的内容仍可能被 IntersectionObserver 判定为可见，不能只凭“进入视口”判断值得播放。

5. 有些静止状态属于现有偏好规则。
宽度低于 1024px、节省流量或已保存暂停偏好时，默认可能保持静态；系统减少动态也会使用静态图。
应把“正在准备动画”“用户暂停”“轻量静态”区分清楚，避免所有静止都被理解为加载失败。

当前文件预算，按实际角色清单核算，单位为十进制 MB/KB：
• 两人活动贴图：1,517,994 字节，约 1.52 MB，共 22 张。
• 两张静态人物图：388,090 字节，约 0.39 MB；与活动贴图是不同请求。
• 清单：43,945 字节，约 44 KB。
• 两张 body 贴图合计 1,167,528 字节，占活动贴图约 77%。
• 当前 dist 渲染器主块：396,775 字节；本地 gzip 估算 116,960 字节，不含所有依赖块，也不是线上传输实测。
• 背景 scene/4-web.mp4 文件约 2.10 MB；文件体积不等于首屏已下载流量。
• 旧预算报告的“全部角色素材约 2.49 MB”还含未在当前清单使用的资源，不能直接当成首次打开的角色下载量。

三、第一轮 P0：让细节动画尽快启动

A. 缩短加载链，保持原画与当前动作参数。
将资源获取与网格组装分开：先从清单收集去重 URL，使用共享 Promise 缓存和有上限的并发队列加载，起始并发设为 4～6，再由实测调整。
网格仍按原始部件次序组装，确保刘海、眼睛、眉毛的遮挡关系一致。
清单请求可与渲染器导入/初始化重叠；只有确认动效启用、页面可见时才触发重资源准备。
先实施有界并发并保留两人原子切换，风险较小。若慢网测试仍显示一人长期拖住另一人，再增加每人独立就绪状态和独立静态回退。
独立切换需要一起调整全局 data-renderer-ready CSS、双人错峰动作逻辑及失败清理，不能只删除一处 await。
现有自定义加载器可以完成这项工作；Pixi Assets 的批量加载与缓存可供参考，不以更换加载库作为前置条件。

B. 让“第一次动作”有明确节奏。
第一帧接管后立即保持连续发梢运动；对头发状态做有界预热或解析初始化，接续现有身体时钟，避免跳位及弹簧从零缓慢追赶。
预热只初始化风动状态，不偷偷推进眨眼、挥手事件，也不改变当前 HAIR_SPEED=2.25、发根约束、嘴部幅度与安全角度。
首次眨眼改为：各人物真正就绪后约 0.8～1.5 秒的窗口内，两人尽量错开约 0.3～0.6 秒；后续继续使用原有 3～7 秒自然间隔。
首次眨眼时序与后台恢复时序分开。后台返回、暂停恢复及站内导航不应反复触发“第一次眨眼”。

C. 角色先获得资源，背景稍后进入。
背景媒体的启动条件改为“角色已就绪或角色流程已明确失败/降级”，再结合页面类型、动效偏好和可见性。
保留可配置的最长等待兜底；弱网失败时先用背景封面，避免继续争抢下载。
允许立即跳过欢迎页，不能要求访客等模型准备好才能阅读。
只有用户主动开启的动效才准备模型；手机默认静态与减少动态模式保持既有规则。

D. 启动测试先补齐，再比较优化结果。
记录：控制器开始、渲染器导入结束、清单结束、每人贴图解码结束、首次完整渲染、首次实际发梢形变、首次眨眼、首次可点击招手。
报告从导航开始计时，也报告从“用户开启动效”开始计时；欢迎页等待用户点击不混入动画加载耗时。
加载态提示放在动效设置里，慢加载时再出现，避免给人物盖一个醒目的进度条。

第一轮完成标准：
• 冷缓存请求瀑布中不存在当前 14 组逐级等待的结构，两个角色的资源能够重叠加载。
• 同一设备与网络条件下，首次完整细节动作的中位耗时比改造前降低至少 40%，并报告 5 次冷启动的最慢值。
• 标准桌面测试条件下，暂定首次发梢动作 ≤2 秒；完整动画就绪后第一次眨眼 ≤1.5 秒。若上线网络条件不支持，先如实报告瓶颈再调整预算。
• 交接没有位置、透明度或轮廓突变，欢迎入场与提前跳过正常。
• 角色失败仍可读文章；暂停、后台和减少动态时不持续绘制。

四、第二轮 P1：降低持续动画开销及无关下载

A. 将帧率问题单独处理。
历史实测：2026-10-17 的 V10 完整博客在本机无头 Edge、20 秒采样中约 27.05 fps，更新/提交耗时 p95 为 39.1ms，自动选择了 30fps。该值不是本次新测，也不代表用户设备或单独 GPU 耗时。
当前两人合计约 29,121 个网格顶点。安奈嘴部细节使身体网格扩展到 146×122，而 mouth 的影响只在局部；每帧仍遍历各网格更新顶点。

建议顺序：
1. 用性能剖析分离顶点计算、内存分配、布局读取、纹理上传和 GPU 绘制，先定位占比。
2. 缓存不随时间改变的顶点权重、局部坐标与约束，复用数值缓冲；逐帧共享三角函数与关节变换，减少顶点循环里的临时数组。
3. 将嘴部高精度网格局限在真正需要的区域，或采用局部加密拓扑；既有轮廓、接缝和三角形不翻折检查作为门槛。
4. 需要时增加“轻量／标准／精细”内部质量档。先确保当前画质的稳定 30fps，再争取有余量设备的 60fps；GPU 顶点变形作为剖析后的升级选项。
5. 质量判断同时参考帧间隔和更新耗时，并设置迟滞，减少频繁切档。全屏画布分辨率、阴影与模糊的成本单独验证，不能把所有卡顿都归因于下载或显卡。

B. 降低活动素材成本。
优先对占比最高的两张 body 贴图做尺寸、透明边缘及压缩质量对照。桌面欢迎场景角色很大，不能直接套用手机分辨率。
手机主动开启动效时使用匹配显示尺寸的独立资源档；桌面保留精细档。
小型眼睛／刘海素材可评估按角色打图集，减少请求；图集边缘要留防串色空间。先证明并发加载收益，再决定是否承担图集构建与 UV 调整成本。
新增质量档用带版本或内容哈希的 URL，清单与贴图同时更新；复用站内部件和浏览器缓存。实际缓存头在部署环境检查，不假定任意头配置会被 GitHub Pages采用。

C. 调整非关键模块的加载时机。
• Pagefind：当前 Navbar 在 DOMContentLoaded 时先 HEAD 再 import。改为首次聚焦搜索/打开面板时初始化，复用同一个 Promise，并让首次输入等初始化完成后继续查询，保留失败重试。
• PhotoSwipe：当前 Layout 顶层已经执行 import("photoswipe")。把导入移进实际打开大图的函数，并评估 lightbox 外壳是否需要全站加载。
• 评论：当前页面有评论区就立即请求。改为滚动接近评论区时准备客户端、样式与数据，并支持带评论锚点直达；站内切页取消旧请求和观察器。
• 图标：Svelte 内固定图标改为本地打包数据或内联 SVG，减少外部图标接口依赖。菜单与搜索图标不必等远端返回。
• 外观面板：主题色已固定，但 DisplaySettings 仍无条件 client:only。按实际是否提供该入口决定是否渲染与加载。
• 图片：头像和装饰按显示尺寸生成 WebP 版本；首屏关键人物不做盲目懒加载，文章下方大图按需加载。
• 音频：当前已使用 waaaa-web.m4a 且点击后才设置 src，沿用这一策略；不重复把原始 MP3 大小当成首屏瓶颈。

D. 背景媒体采用页面级预算。
首页标准模式先限制为中央视频和最多一段重点拼贴同时播放；其余保留封面，按需轮换。这是待视觉确认的起始方案。
文章页以静态拼贴和边缘角色为主，专注阅读时停止角色与背景绘制。
只暂停视频不能撤销已经完成的下载；要在设置 src 前决定是否需要请求。
手机默认静态；手动开启动效时优先角色，背景视频仍受独立预算约束。音乐播放状态单独管理。

第二轮完成标准：
• 同一测试机先达到稳定 30fps：60 秒采样平均 ≥29fps，帧间隔 p95 ≤40ms；角色更新/提交 p95 暂定 ≤20ms，留出交互与绘制余量。
• 60fps 仅作为高性能设备的进一步目标；真实手机、集显与高 DPI 分别记录。
• 活动贴图以从 1.52 MB 降到约 1.0～1.2 MB 为试验目标，原画轮廓和眼部质量优先；未通过画面对照则不采用压缩版本。
• 未打开搜索、未点大图、未接近评论区时，对应重量级模块不抢角色启动资源。
• 静态或减少动态模式不请求完整角色模型；后台动画停止；同一会话站内跳转仅保留一套画布和监听器。

五、第三轮 P2：把已有美术资源组织得更好

1. 首页与文章页使用不同的阅读底色。
桌面现有截图中，人物眼睛和面部明显透过文章卡片；当前卡片约 88% 不透明并叠加背景模糊。
先保留双角色位置与原画，将首页卡片不透明度试调到 94%～97%，正文卡片到 98%～100%，用轻边框和浅阴影表达层次；减少正文区域的大面积 backdrop-filter。
首页继续展示人物与拼贴。文章页通过更实的底色和专注阅读控制保持视线稳定，人物尺寸与锚点的大调整另做预览对比。

2. 播放器与动效入口形成统一停靠区。
现有截图中，底部居中的播放器覆盖文章内容，手机动效按钮也压住卡片。
桌面优先侧栏停靠；窄屏用靠边的 44～48px 唱片入口，展开后显示完整控制，保留关闭入口与底部安全间距。
动效、角色显示、专注阅读合并到一个简洁设置面板。音乐独立控制，不随阅读模式切换而重播或被强制暂停。
检查搜索、目录和评论输入时的避让；继续保留跨页播放。

3. 首页卡片增加内容层级。
增加“全部／学习与科研／游戏／日常／公告”的轻量分类入口，落地时以现有真实分类为准，避免自动改写文章元数据。
长文突出标题、两行摘要、阅读时间；短日记更紧凑；游戏长评支持明确的剧透文字标识。
减少整列大箭头占位、重复图标和过长标签。分类区别主要由小徽章与局部配色表达，共享字号、圆角和间距。
保留粉白基调，深色模式采用已有暖紫黑背景，为卡片、元信息、焦点和播放器逐项校对。

4. 手机首屏与文章头部更紧凑。
首页将作品拼贴、简介和“文章与日常”标题区整理为紧凑组合，让第一篇文章更早进入视口。
文章页直接出现标题、日期、摘要与折叠目录，作者名片移至文末或缩为作者行。
为 1024～1535px 视口提供可用的目录入口，不依赖当前 1536px 才显示的外侧目录。
全文表格、公式、长代码与下载模块都保持区域内滚动。

5. 欢迎演出只用于合适入口。
当前会话首次访问判定没有区分路径。建议首页首次访问保留欢迎场景，外部直达文章、归档、友链时直接进入内容；另提供重看入口。
欢迎入场、角色资源准备及进入正文互不阻塞，保留点击/Escape 跳过。
页面级状态需接入 Swup 的 page:view/content:replace；当前配置不会自动更新 body class，不能只在服务器首次渲染时设置文章模式。

第三轮完成标准：
• 首页、科研长文、游戏长评和短日记均有浅/深主题对照。
• 390×844、768px、1280×720、1920×1080 下，播放器不遮正文、目录和评论输入；无整页横向滚动。
• 手机直达文章首屏可见标题与正文开头，不被欢迎演出和大名片阻挡。
• 关于页兴趣墙、更多皮肤和新彩蛋放在上述三轮之后，按现有文章和站长提供内容扩展。

六、统一测量与发布门槛

建立两个固定环境：
标准桌面：1280×720，固定浏览器版本及机器，分别测试 DPR 1 和 2；10Mbps 下载、50ms RTT，不额外降低 CPU。
受限环境：1.6Mbps 下载、150ms RTT、4 倍 CPU 降速；该组合是可复现的实验条件，不等同于所有真实手机。
各跑 5 次冷缓存与 5 次热缓存，记录中位数和最慢值；小样本不宣称为真实用户 p75/p95。
冷缓存必须清理 HTTP 缓存；本地无压缩预览与线上压缩传输分开报告。首页首次欢迎、首页跳过、文章直达、站内跳转分别记录。
手机默认静态时没有“等待动画启动”的 SLA；主动开启后从点击时刻计时。加入暂停偏好、减少动态、后台恢复、资源失败和 WebGL 失败场景。
动画帧统计在进入稳定状态后采样 60 秒，记录平均帧率、帧间隔 p95、更新/提交 p95、长任务与当前质量档。

网页整体目标：LCP ≤2.5 秒、INP ≤200ms、CLS ≤0.1。正式核心网页指标按真实用户第 75 百分位并区分移动/桌面；少量本地实验只能作为实验室基线。
欢迎页不能遮蔽阅读体验的评估：另记录“文章真正可读”的时刻，避免只看首屏图片指标。

复用现有测试：角色动画、原画一致性、发根/嘴部约束、点击命中、欢迎跳过、后台/暂停和跨页单画布；新增真正针对启动时限、请求并发、失败清理和首眨眼的验证。
每轮给出同条件前后数据及截图，经过相关测试、Astro 检查与正式构建后再进入下一轮。此次仅交付方案，没有性能提升结果可供宣称。

七、建议拆分的实施批次

批次 1：启动计时 → 共享资源队列与并发 → 首次眨眼 → 背景让出加载资源。直接解决当前反馈，保持角色原画和动作风格。
批次 2：帧耗时剖析 → 顶点计算与局部网格优化 → 资源分档 → 搜索/大图/评论/图标按需准备。
批次 3：卡片底色 → 播放器停靠 → 手机文章头部 → 欢迎入口规则 → 首页分类及卡片。
每批独立验收，避免角色拓扑、加载机制和全站视觉同时变化，使回归难以定位。
